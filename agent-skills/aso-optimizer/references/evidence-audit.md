# ASO 证据审计

判断材料能够和不能够证明什么。不要在本 Skill 中把证据直接变成最终关键词、元数据或实验建议。

## 工作流程

1. 盘点每个来源的文件名、提供方、App、平台、商店地区、语言、指标日期、导出日期和时间范围。
2. 对 CSV 文件运行：

```bash
python3 scripts/inspect_aso_csv.py <file> [<file> ...]
```

3. 保留原始文件，不得覆盖、合并或静默清洗源数据。
4. 对数据分类：
   - `first_party`：我方 App 的官方观察数据。
   - `market_observation`：第三方关键词、排名、榜单或竞品数据。
   - `estimated`：模型估算的下载、收入、难度或流量。
   - `qualitative`：截图、商店文案、报告或分析笔记。
   - `product_fact`：已验证的产品能力或限制。
5. 应用 [evidence-contract.md](evidence-contract.md)。
6. 识别不兼容的指标。除非提供方明确说明量表相同，否则不得平均不同平台的热度、难度、指数或估算量。
7. 找出阻碍比较的缺失维度：市场、平台、语言、日期、App 身份、指标定义或分母。
8. 判定数据阶段 `M0`–`M3`。
9. 输出证据报告。

## 特殊处理

- 竞品关键词覆盖只能证明竞品曾出现在该词下，不能证明我方应当投放该词。
- 没有每日原始值时，排名截图只作为方向性证据。
- “落榜”、缺行和空白是不同状态，不得统一转换为排名 0。
- App Store Connect 和 Google Play Console 只对我方 App 及导出维度具有权威性。
- RevenueCat 正确配置后可作为订阅生命周期和权益来源；应核对差异，不得直接覆盖商店汇总。
- 产品负责人陈述属于产品事实，不属于需求证据。

## 输出

严格使用以下结构：

```markdown
# 证据审计

## 数据阶段
M0 / M1 / M2 / M3

## 来源清单
| 来源 ID | 提供方 | App | 平台 | 市场 | 时间范围 | 类别 | 新鲜度 |

## 数据质量
| 来源 ID | 行数 | 重复项 | 缺失字段 | 指标限制 |

## 结论支持
| 结论或问题 | 等级 | 支持来源 | 冲突 | 能够证明什么 |

## 不受支持的结论
- ...

## 可安全开展的后续任务
- ...

## 必须补充的数据
- ...
```

不得输出虚假精度。无法确定时使用 `unknown`。
